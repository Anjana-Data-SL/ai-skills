# Anjana Data Platform - Permissions Catalog

Complete catalog of the 25 permission types available in Anjana Data Platform **v26.1**.

## Permissions That Do NOT Require Object Subtype

These permissions use a fixed `subType` — no need to ask the user for an object subtype.

### Module / Platform Access

| Permission (Natural Language) | `action` | `subType` |
|-------------------------------|----------|-----------|
| Acceso al portal de datos | `PLATFORM_ACCESS` | `ANJANA` |
| Acceso al panel de configuración / administración | `ADMIN_ACCESS` | `ANJANA` |
| Permiso de uso de API | `API_ADMIN` | `ALL` |
| Acceso a la documentación de la API | `API_DOC` | `ALL` |
| Acceso al linaje | `LINEAGE_ACCESS` | `ALL` |
| Acceso a los workflows | `WORKFLOW_ACCESS` | `ALL` |
| Acceso al módulo Catálogo | `CATALOG_ACCESS` | `ALL` |
| Acceso al Workspace | `WORKSPACE_ACCESS` | `ALL` |
| Acceso al módulo Trabajos | `JOBS_ACCESS` | `ALL` |
| Solicitar acceso a datos (marketplace / carrito) y acceso al módulo Marketplace | `ADHERENCE_ACCESS` | `ALL` |
| Ver información de usuarios adheridos | `ADHERENCE_VIEW` | `ALL` |
| Editar la "Información de acceso" de un activo (texto que ven los usuarios con acceso) — **26.1+ únicamente** | `EDIT_ACCESS_INFO` | `ALL` |

## Permissions That REQUIRE Object Subtype

For these permissions, ask the user for the object subtype. The subtype must be provided in **uppercase, without spaces or special characters**, exactly as it is named in Anjana Data Platform.

### Without Additional Restrictions

| Permission (Natural Language) | `action` | `subType` | Notes |
|-------------------------------|----------|-----------|-------|
| Extracción de metadatos de `<SUBTYPE>` | `AUTOMATIC_METADATA` | `<SUBTYPE>` | Ask user for the object subtype |
| Creación o modificación de `<SUBTYPE>` | `CREATION_MODIF` | `<SUBTYPE>` | Ask user for the object subtype. Also enables the creation wizard for that subtype (in 26.1). **NEVER assign with `subType=DATASET_FIELD`** — fields are child entities created inline within a DATASET, not standalone via wizard. |
| Borrado de `<SUBTYPE>` creados por el propio usuario | `DELETE_MY_OBJ` | `<SUBTYPE>` | Ask user for the object subtype. **NEVER with `subType=DATASET_FIELD`**. |
| Borrado de `<SUBTYPE>` creados por cualquier usuario | `DELETE_ALL` | `<SUBTYPE>` | Ask user for the object subtype. **NEVER with `subType=DATASET_FIELD`**. |

### Only for Entities (NOT Relationships)

These permissions can only be assigned to object subtypes that are **entities**, not relationships. Ask the user to confirm that the subtype is an entity before proceeding.

| Permission (Natural Language) | `action` | `subType` | Restriction |
|-------------------------------|----------|-----------|-------------|
| Propietario de `<SUBTYPE>` | `ORGANIZATIONAL_UNIT_OWNER` | `<SUBTYPE>` | **Entity only** — ask user to confirm it is an entity, not a relationship |
| Cambio de unidad organizativa de `<SUBTYPE>` | `CHANGE_OU` | `<SUBTYPE>` | **Entity only** — ask user to confirm it is an entity, not a relationship |

### With Excluded Subtypes (CHANGE_STATUS only)

| Permission (Natural Language) | `action` | `subType` | Excluded Subtypes |
|-------------------------------|----------|-----------|-------------------|
| Cambio de estado de `<SUBTYPE>` | `CHANGE_STATUS` | `<SUBTYPE>` | Cannot use with: DATASET, DSA, PROCESS, INSTANCE, SOLUTION |

### Deprecation (no exclusions)

`DEPRECATION` works for **all** object subtypes including the native data-catalog ones (`DATASET`, `DSA`, `PROCESS`, `INSTANCE`, `SOLUTION`) in versions **25.1, 25.2 and 26.1**.

| Permission (Natural Language) | `action` | `subType` |
|-------------------------------|----------|-----------|
| Deprecación / descontinuar `<SUBTYPE>` | `DEPRECATION` | `<SUBTYPE>` |

### IMPORTANT — Native (system-managed) subtypes

Some objectSubTypes are **native to the platform** and their instances are auto-generated by Anjana, not by user actions. They have `createWorkflow == "WF_NATIVO"` in the API response. **Do NOT assign user-action permissions to them**, especially when iterating over all subtypes in a bulk operation.

Known native subtypes (the API may surface more, depending on installation):

| `subType` | Type | Description | Why no user permissions |
|-----------|------|-------------|-------------------------|
| `ADHERENCE` | RELATIONSHIP | DSA acceptance by a user (DSA → USER) | Created automatically when a user adheres to a DSA via the Marketplace |
| `STRUCTURE` | RELATIONSHIP | Fields belonging to a dataset (DATASET → DATASET_FIELD) | Auto-derived from dataset metadata |
| `DSA_CONTENT` | RELATIONSHIP | Entities included in a DSA (DSA → any) | Managed by the DSA workflow |
| `INSTANCE_DATASET_IN` / `INSTANCE_DATASET_OUT` | RELATIONSHIP | Inputs/outputs of a process instance | Managed by the runtime that creates instances |
| `INSTANCE_PROCESS` | RELATIONSHIP | Process that generated an instance | Managed by the runtime |
| `SOLUTION_OWNED_INSTANCE` / `SOLUTION_RELATED_INSTANCE` | RELATIONSHIP | Instances owned/related to a solution | Managed by the Solution module |

**Permissions that should NOT be assigned to native subtypes**:
`CREATION_MODIF`, `DELETE_MY_OBJ`, `DELETE_ALL`, `ORGANIZATIONAL_UNIT_OWNER`, `CHANGE_OU`, `CHANGE_STATUS`, `DEPRECATION`, `AUTOMATIC_METADATA`. These trigger user-facing wizards or actions that don't apply.

**Bulk-assignment rule**: when iterating `GET /api/filter/objectSubTypes` to give a role permissions over many subtypes (e.g., for an admin role), **filter out** any subtype with `createWorkflow == "WF_NATIVO"`. Only assign permissions to subtypes with `createWorkflow == "AUTO"` or any other custom workflow identifier.

Example filter in Python:
```python
items = response.json().get("content", [])
user_creatable = [i for i in items if i.get("createWorkflow") != "WF_NATIVO"]
```

## Notes on v26.1 Changes vs Previous Versions

- `ACCESS` / `ALL` (portal access) → renamed to `PLATFORM_ACCESS` / `ANJANA`.
- `ACCESS` / `ADHERENCE` (request data access) → renamed to `ADHERENCE_ACCESS` / `ALL`. Now also grants access to the new Marketplace module.
- `ADMIN` / `ANJANA` (admin panel) → renamed to `ADMIN_ACCESS` / `ANJANA`.
- `WIZARD` / `ALL` → **removed in 26.1**. In 25.x this permission is **mandatory** for any role that should see the creation wizard ("+") in the UI. **Versions 25.1 and 25.2: assign `WIZARD/ALL` to every role that has any `CREATION_MODIF` permission, otherwise the user logs in but cannot see the option to create new entities/relations.**
- New module access permissions: `CATALOG_ACCESS`, `WORKSPACE_ACCESS`, `JOBS_ACCESS`, `API_DOC`, `ADHERENCE_VIEW` (all with `subType: ALL`). Workspace and Jobs previously did not require any permission.
- New object-tab visibility permissions: `OBJ_RELATIONS_ACCESS`, `OBJ_STAKEHOLDERS_ACCESS`, `OBJ_AUDIT_ACCESS`, `OBJ_VERSIONS_ACCESS`, `OBJ_SAMPLE_DATA_ACCESS` (all with `subType: ALL`).

## Per-Version Baseline Permissions

The following are minimum baseline permissions every operational role needs. Without them, the UI hides functionality even if `CREATION_MODIF` permissions exist for specific subtypes.

### Version 25.1 / 25.2

| Permission | Notes |
|---|---|
| `ACCESS` / `ALL` | Portal access. Without it, the user cannot log into the data portal. |
| `WIZARD` / `ALL` | **Mandatory** — enables the "+" creation wizard. Required for any role that has at least one `CREATION_MODIF` permission. Without `WIZARD/ALL` the wizard is invisible even if the user has `CREATION_MODIF` on multiple subtypes. |
| `LINEAGE_ACCESS` / `ALL` | Lineage view. |
| `WORKFLOW_ACCESS` / `ALL` | Workflow tab. |
| `ACCESS` / `ADHERENCE` | Request data access (Marketplace pre-26.1). |

### Version 26.1

| Permission | Notes |
|---|---|
| `PLATFORM_ACCESS` / `ANJANA` | Portal access (renamed from `ACCESS/ALL`). |
| `CATALOG_ACCESS` / `ALL` | Catalog module. |
| `WORKFLOW_ACCESS` / `ALL` | Workflow tab. |
| `LINEAGE_ACCESS` / `ALL` | Lineage view. |
| `ADHERENCE_ACCESS` / `ALL` | Marketplace + data request. |
| (no `WIZARD/ALL`) | The wizard is automatically inferred from any `CREATION_MODIF` permission. Do NOT create `WIZARD/ALL` in 26.1 — the action is no longer recognized. |

**Validation step**: after assigning permissions to a role, test by logging in as a user with that role and confirming the wizard appears. If it doesn't on 25.x, the role is missing `WIZARD/ALL`.

## Subtypes that Should NEVER Receive User-Action Permissions

In addition to the **native subtypes** rule (`createWorkflow == "WF_NATIVO"`), there is one specific subtype that must NEVER receive `CREATION_MODIF`, `DELETE_MY_OBJ`, `DELETE_ALL`, `ORGANIZATIONAL_UNIT_OWNER`, `CHANGE_OU`, `CHANGE_STATUS`, `DEPRECATION`, `AUTOMATIC_METADATA`:

### `DATASET_FIELD`

`DATASET_FIELD` is a **child entity** that exists only inside a `DATASET`. It is created and managed inline through the parent dataset's editor (the "Estructura" tab), not through the standalone creation wizard. Assigning `CREATION_MODIF/DATASET_FIELD` produces an orphan permission that:
- Adds `DATASET_FIELD` to the role's wizard catalog, but the wizard cannot create it standalone (no parent context).
- Confuses the user with a non-functional option.

**Rule**: when iterating subtypes to assign user-action permissions, always exclude `DATASET_FIELD`. To grant a role the ability to manage dataset fields, give it `CREATION_MODIF/DATASET` — that automatically authorizes managing fields within owned datasets via the structure tab.

## Validation Checklist

Before sending a permission creation request:

1. Verify `action` is one of the 25 valid values of version 26.1 listed above (or, for 25.1 / 25.2, one of the equivalents in "Notes on v26.1 Changes" and "Per-Version Baseline Permissions")
2. Verify `subType` is `"ALL"`, `"ANJANA"`, or a valid object subtype in uppercase
3. For `PLATFORM_ACCESS` and `ADMIN_ACCESS`: `subType` must be `ANJANA`
4. For `ORGANIZATIONAL_UNIT_OWNER` and `CHANGE_OU`: confirm the subtype is an entity (not a relationship)
5. For `CHANGE_STATUS`: confirm the subtype is NOT one of: DATASET, DSA, PROCESS, INSTANCE, SOLUTION (`DEPRECATION` has no such restriction — it is valid for those subtypes)
6. **For user-action permissions (`CREATION_MODIF`, `DELETE_MY_OBJ`, `DELETE_ALL`, `ORGANIZATIONAL_UNIT_OWNER`, `CHANGE_OU`, `CHANGE_STATUS`, `DEPRECATION`, `AUTOMATIC_METADATA`)**: confirm the subtype is **not native** (`createWorkflow != "WF_NATIVO"`). Native subtypes (e.g., `ADHERENCE`, `STRUCTURE`) are managed by the platform — these permissions create orphan entries with no UI effect. Especially relevant when iterating over all subtypes from `GET /api/filter/objectSubTypes`.
7. **For user-action permissions (same list as point 6)**: confirm the subtype is **NOT `DATASET_FIELD`**. Dataset fields are child entities managed inline within the parent DATASET; user-action permissions on `DATASET_FIELD` produce orphan, non-functional entries.
8. **For versions 25.1 / 25.2**: if assigning `CREATION_MODIF` to a role, confirm that role also has `WIZARD/ALL`. Without it the wizard never appears in the UI even though the permission is set in the database. Not applicable in 26.1 (the action was removed and the wizard is inferred from `CREATION_MODIF`).
9. Verify that `role` is the href of a role that **exists in this environment**: `GET <BASE_URL>/gateway/api/portuno/roles/<id>` must return it (id = number at the end of the href; usual format `<PORTUNO_HREF>/roles/<id>`). Do not reject an href only because of its host, and do not create the permission if the role is not found

## Request Body Template

```json
{
    "action": "<ACTION_KEY>",
    "subType": "<SUBTYPE_KEY>",
    "role": "<ROLE_HREF_URL>"
}
```

## Example: Assigning Multiple Permissions to a Role

To give a role full data management permissions in v26.1, create multiple permission requests (one per permission):

1. Portal access: `{ "action": "PLATFORM_ACCESS", "subType": "ANJANA", "role": "<href>" }`
2. Catalog module access: `{ "action": "CATALOG_ACCESS", "subType": "ALL", "role": "<href>" }`
3. Create datasets (also enables the wizard for DATASET): `{ "action": "CREATION_MODIF", "subType": "DATASET", "role": "<href>" }`
4. Delete own datasets: `{ "action": "DELETE_MY_OBJ", "subType": "DATASET", "role": "<href>" }`
5. Workflow access: `{ "action": "WORKFLOW_ACCESS", "subType": "ALL", "role": "<href>" }`
6. View object relations tab: `{ "action": "OBJ_RELATIONS_ACCESS", "subType": "ALL", "role": "<href>" }`
